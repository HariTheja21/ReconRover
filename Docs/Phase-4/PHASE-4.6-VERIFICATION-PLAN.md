# Phase 4.6: ESP32 Hardware Telemetry System - Verification Plan

## Executive Summary
This document outlines the verification strategy for Phase 4.6 (ESP32 Hardware Telemetry System). The objective is to rigorously verify that the C++17 telemetry pipeline correctly extracts physical hardware states, schedules them accurately according to configured frequencies, and seamlessly encodes the data into protocol-compliant UART frames.

## Verification Objectives
- Validate the `TelemetryScheduler` correctly tracks sub-millisecond deltas without stalling the RTOS task.
- Ensure the `TelemetryEncoder` correctly packs multi-byte integers (e.g., Battery voltage, Motor RPM) strictly in Big-Endian format.
- Verify `TelemetryPacketBuilder` correctly calculates the XOR CRC8 checksum over the payload.
- Prove that the sequence numbering system correctly rolls over at 255.
- Confirm zero dynamic allocation is enforced throughout the telemetry lifecycle.

## Verification Scope
The scope encompasses the `ESP32_ROVER/main/telemetry/` subsystem. Serial hardware UART transmission delays and physical sensor polling are simulated.

## Audit Strategy
1. **Static Architecture Analysis:** Review C++ memory structures to guarantee no heap usage. 
2. **Logic Emulation:** Utilize the `test_telemetry.cpp` internal test suite to emulate FreeRTOS ticks.
3. **Protocol Cross-Validation:** Assert the generated byte output exactly matches the `PacketFramer` requirements deployed on the Raspberry Pi in Phase 4.3.

## FreeRTOS Audit
- Ensure that the `UartTransmitCallback` injection allows the system to enqueue packets non-blockingly, safeguarding the telemetry gathering loop from slow UART TX boundaries.

## Runtime Audit
- Verify the scheduler executes $O(1)$ constant time boolean logic.

## Memory Audit
- Verify that `TelemetryPacketBuilder` and `TelemetryEncoder` utilize static 16-byte stack buffers rather than heap vectors.

## Internal Test Matrix
1. **Timing Validation:** Step the emulator exactly 99ms, assert no motor packet. Step 1ms, assert motor packet (100ms interval).
2. **Endianness Validation:** Encode a 16-bit integer `0xABCD`, assert `buffer[0] == 0xAB` and `buffer[1] == 0xCD`.
3. **Rollover Validation:** Force sequence ID to `255`, generate a packet, assert the next packet's sequence ID is `0`.
4. **CRC Check:** Generate a known packet, manually compute the XOR, assert the builder's output matches perfectly.
5. **Callback Health:** Assert the telemetry engine correctly invokes the injected function pointer with the exact pointer to the packet buffer and length `9`.

## PASS / FAIL Criteria
- **PASS:** 100% test success, zero heap allocation, sub-millisecond execution time, perfect protocol matching.
- **FAIL:** Dynamic memory allocations, blocking logic, dropped timestamps, or Little-Endian packing errors.
